# 逐页原文片段入库（2026-10-28 六书）

本工具配合本轮 PDF 检查/OCR 中间数据使用，产物采用现有 `KnowledgeItem` 六字段，不改变线上
Java 结构或检索算法。旧的 LLM 一句话知识点保留；新书保留有出处的原文片段，避免同名知识点
跨页覆盖以及过度摘要导致的信息损失。不是把全文直接塞进模型上下文。

## 输入和输出

运行 `build_book_chunks.py <逐页结果目录> <候选输出目录>`。
输入 `inventory.json` 描述六本原始 PDF 的路径、SHA256、页数、低文字页；
每书目录有 `text-pages.json`、`ocr/NNNN.json`，需重识别的书有 `ocr-refined/NNNN.json` 并标记
`preferRefinedOcr=true`。任何待 OCR 页未完成就拒绝最终构建；`--allow-pending` 仅用于副本预演。

输出 `new-items.json`、`manifest.json` 和 `source-pages.json.gz`。原文按物理 PDF 页定位，
600 字符上限、90 字符重叠，在句末优先切分；不同书或不同页同名内容不会被丢弃。
ID 包含原 PDF 哈希、页、片段序号、文本哈希。清单含原文件摘要、逐书计数、明确排除的封面/
空白/目录等页、内容摘要和原文归档摘要。被排除页仍在原文归档中，不静默假装读取失败页为空白。

标题由书名和片段开头生成，表示原文位置，不冒充模型提炼的概念名称。
这批条数应表述为“知识条目/原文片段”，不能据此声称独立知识概念增加了相同数量。

## OCR 与质量

`src/test/java/.../extract/BookPageOcr.java` 复用项目已有 RapidOCR，离线逐页保存结果；
`--images` 模式读取 PDFium 渲染页图，适用于 PDFBox 无法处理原文件色彩空间的情况。
源码 PDF 不改，模型和 native 资源复用已有依赖。测试入口不打入业务包。

本轮发现《存在与时间》隐藏文字层漏字，且 PDFBox 对其中部分图像色彩空间渲染异常，
因此改用 PDFium 实际可见页图重新识别，不能把原文字层“非空”直接视作质量合格。
OCR 并非零误差，图表/公式/双栏结构尚未完整语义化，仍需结合具体问题查看原页。

## 验收与发布

- `python test_build_book_chunks.py`：检查重叠不丢字、跨页/跨书 ID、清洗、正文省略号不会误删为目录。
- `src/test/server/book_ingest_verify.py`：仅本轮固定布局的副本准备/补向量/评测工具。
  复用原 12925 条匹配云向量，新增/变化片段显式分批补齐；查询不承担补向量。
- `src/test/server/book_publish.py`：全量副本通过后停写备份知识/向量匹配对，再发布并重启。
  原业务包、账号配置、域名不动；临时普通账号逐本真实问答，验后停用；失败恢复旧知识对。

评测保留既有 46 题回归与新增每书 3 题，按来源+物理页共同判分。新增题是公开的开发烟测集，
不是独立盲测或全书答案准确率。初始标注修正必须留修正理由；不能把修正标签当算法提升。
自然问题直接检索与 Agent 关键词改写的完整问答是两种口径，分别留证。

原 PDF、逐页全文、向量、凭据和生产数据不入 Git。入库前备份及最终具体条数/哈希以本轮
桌面验收报告和服务器清单为准。这个固定六书脚本不应直接对别的生产布局重复执行。
